## 発見事項

1. **fast-apply 純粋意味論は分布内で高機能**: タグ形式の MALFORMED は 0 件、完全一致 65%、sim≥0.95 で 80%。残り 20% の実エラーは「挿入ブロック欠落」「要素欠落」「別関数本体の生成」で、いずれも `... existing code ...` 省略やファイルサイズ(4k tok 超)と相関が見られる。
2. **`validateStructure` の prefix 必須チェックが誤爆 5/20(25%)**: 更新がファイル**先頭**(import ブロック等)を正当に変更するケースで、先頭 20% prefix の `startsWith` 検証が誤って失敗する。出力は GT とバイト一致にもかかわらず `STRUCTURE_MANGLE_ERROR` で拒否された。**ToDo 4 で予期された問題が実測で確認された**。pipeline レベルでは成功率を 80% → 55% に引き下げている。
3. **タイムアウト**: ローカル 7B は入力 4k tok 超で 60〜130s 必要。`FAST_APPLY_TIMEOUT` 既定 60s では rs/large 等が TIMEOUT になる。ローカルモデル運用では 180s+ が妥当(クラウド高速モデルでは現状のまま可)。
4. **end-to-end 確認(副産物)完了**: 実エンドポイント + anchoredit 書き込みを `fa_merge` ツールで検証。
   - 成功例: `harness/tmp/e2e-big.py` の `main()` へ `print` 行を追加 — anchoredit が hash 検証付きで正しく書込。
   - 失敗例: 小ファイル先頭変更では上記 2 と同じ誤爆で `STRUCTURE_MANGLE_ERROR`(リトライしても再現)。
   - 注意点: 上記 3 のタイムアウト問題は e2e 経由でも同様に効く。

## 推奨アクション(ToDo 反映用)

- **優先**: `validateStructure` の prefix チェック緩和(例: prefix 行の「存在」チェックに置き換え、先頭変更ケースへの誤爆排除)。誤爆 5/20 が解消すれば pipeline 成功率は 80% まで回復する見込み。
- README/SPEC に「ローカルモデル運用は `FAST_APPLY_TIMEOUT=180000`+ を推奨」を追記。
- 自然言語 A/B 実験(ToDo 2)の比較基準: 本ベースライン(完全一致 65% / sim≥0.95 80% / 実エラー 20%)。
